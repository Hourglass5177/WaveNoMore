# 独立试玩帧耗时调查与后台写谱器休眠

2026-09-09，基于 `develop/editor/pet@39cb28c8`。本轮修改写谱器工作区、预览会话和试玩进程轮询；没有修改正式判定、音频时间、随从或震动实现。

## 已确认的开销与修改

暂停试听后，内嵌 SubViewport 原来仍是 `UPDATE_ALWAYS`，持续绘制高分辨率关卡；试玩启动器还在每个渲染帧读状态 JSON、查询进程是否存活。两者都贯穿整个试玩，而非只发生在某个音符附近。

现在仅在“专用试玩仍在运行、整个写谱器失焦、试听暂停”同时成立时，冻结内嵌预览纹理、停掉预览场景处理，并把后台工具限制为至多 15 FPS。正在进行的分批定位暂停工作，切回后继续；待编译内容留到前台再处理。自动保存、任务处理和进程监测继续运行，前台键鼠编辑保留。切回或试玩退出时恢复原帧率、原预览状态，不重新装谱。

试玩状态改为约每 250 ms 查询一次，首次启动立即检查；这是进程生命周期查询频率，不是输入、声音或游戏更新频率。原生弹窗属于同一应用，打开属性弹窗不会被当成切出应用。

## 测量与限制

本机 Core Ultra 9 185H、RTX 4060 Laptop、驱动 610.88，Godot 4.7.2 OpenGL Compatibility。读取用户 `test/song.json` 的 normal 难度，不保存到原工程。游戏窗口 2560×1440，后台工具暂停预览在 34.832 秒。使用真实游戏入口与 Tap/Hold 物理键事件，逐帧记录单调时钟间隔。

初轮“后台正常绘制／测量脚本直接冻结”分别测到 P95 13.090／9.790 ms。但窗口焦点可能影响播放，因此另做记录实际歌曲起止时间的对照，测量时关闭游戏失焦暂停；下表每轮均实际推进约 16 秒、处理 28 次按下或松开，未进入暂停。

| 条件 | 平均帧间隔 ms | P95 ms | 最大 ms | 超过 16.667 ms 的帧 |
|---|---:|---:|---:|---:|
| 游戏单独运行 | 6.769 | 10.692 | 19.494 | 2 / 2365 |
| 后台写谱器正常绘制 | 6.757 | 11.853 | 27.917 | 18 / 2368 |
| 正式休眠入口，第一轮 | 8.995 | 14.559 | 24.536 | 31 / 1779 |
| 正式休眠入口，复测 | 6.131 | 9.546 | 17.876 | 2 / 2610 |

复测中游戏全部 2610 帧保持前台；后台工具每五秒记录一次，始终为暂停预览、15 FPS、Viewport 禁止更新。第一轮休眠结果更慢，说明环境波动仍明显，不能挑最好的一轮宣称稳定提升百分比。游戏单独运行样本未绑定震动设备，另三轮检测到 SDL 双强度后端，也不能用它们证明震动的有无导致性能差异。

另将正式会话和震动维护移到测量脚本手动调用，单独记录方法耗时：会话平均 2.861 ms / P95 4.209 ms；震动维护平均 0.101 ms / P95 0.164 ms。该诊断改变了调用位置，只用于定位耗时，不作为正式帧率对照；也不包含所有从其他路径发出的震动调用。当前没有证据需要关闭震动。

汇总见 [测量数据](chart-editor-trial-performance.json)。完整逐帧数组、测量脚本和日志保留在本机 `builds/trial-performance-0909/`。`strikes-final` 因同样墙钟时长只处理 20 个输入，没有纳入上述改善比较。Godot 的稀疏 `TIME_PROCESS` 监视值混有初始化，未拿它冒充逐帧耗时。

这次消除了确定的后台额外工作，并测到了长帧，但没有证明用户整段卡顿的全部原因。16 秒 Tap/Hold 输入样本不覆盖全曲后半段 Tuning/Ghost、真人双摇杆或不同设备下的显示帧节奏；后续反馈如仍卡，应按发生段落进一步采集，不能只凭平均 FPS 断言流畅。
