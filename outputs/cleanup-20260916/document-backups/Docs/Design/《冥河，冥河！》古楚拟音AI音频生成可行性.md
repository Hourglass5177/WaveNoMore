# 《冥河，冥河！》古楚拟音 AI 音频生成可行性

调研日期：2026-09-09。

承接《古楚语词汇、拟音与 PV 配音调研》。本报告研究如何把已经选定的拟音变成音频。完成了官方文档、论文和部分源码核查，**尚未运行模型生成古楚音频，也没有获得这些模型在本项目上的听测结果**。下文的可行性与优先级是据此提出的工程判断。

## 1. 结论与建议

已有可借用的方案，值得做小样。本次未找到同时具有明确楚方言拟音依据、开放读音接口、可复核测试材料的现成“古楚语任意句子朗读器”。最有希望的方式是：

**指定句子 → 按固定方案查定 IPA → 转成引擎实际接受的音素 → 生成候选音频 → 核对发音 → 表演、吟唱与混音。**

| 目标 | 本次判断 | 先试什么 |
| --- | --- | --- |
| 给播音同学提供固定短句的学习音频 | 值得试，仍须核对模型是否发对 | Eleven v3 的直接 IPA 输入；需要本地控制时试 IMS-Toucan |
| 生成可进入 PV 的短旁白 | 有条件可行，通常需要多次生成和逐句挑选 | IPA 合成与真人试录并列比较 |
| 生成重复祭辞、吟唱 | 有较成熟的编辑工作流，特殊古音仍需映射或补录 | Synthesizer V 一类可逐音素编辑的歌声合成器 |
| 同一读法制作不同角色声音 | 有现成声音转换方案；输入发音要先可靠 | 真人或合成底稿 → Seed-VC 等音色转换 |
| 输入任意汉字，模型自动给出准确古楚发音 | 目前没有足够证据支持直接依赖 | 先建立项目用词表和拟音规则 |
| 用一首四分多钟歌曲训练通用古楚 TTS | 不适合作为当前 PV 的首选 | 先积累所需短句，不先做通用模型 |

优先顺序：**短旁白先试 Eleven v3；吟唱先试可编辑音素的歌声合成；需要自行开发时优先研究 IMS-Toucan。**已经有读准的底稿时，再考虑声音转换。专门微调放在确实需要大量新增台词之后。

## 2. 与本任务接近的先例

### 2.1 古音与计算机合成本身有先例

Jeffrey R. Tharsen 的《From form to sound 自形至聲》讨论前现代汉语音韵的可视化与声音呈现，并讨论把语音表示转换为合成器可读输入。随文仓库有杜甫相关语音转写、音素材料及其他语言示例。它证明这类数字人文工作有既有路径，不能据此认定已提供战国楚语的成熟音频模型。

来源：[论文](https://home.uchicago.edu/~jcarlsen/academics/downloads/Tharsen_IJDH2022_FromFormToSound.pdf)、[作者随文仓库](https://github.com/thars3n/IJDH_phonetics)。本次核对论文检索内容及仓库材料目录，未复现其完整流程。

另有创作者在《送别》的历代汉字音演示中明确说明使用 eSpeak 合成，选集中包含上古和中古版本。这是方法上的相近作品，不是古楚发音经过学术验证的证明。[创作者发布说明](https://www.bilibili.com/video/BV16E411d7cv/)

你提供的乐正绫视频则是更直接的项目参考：先由人确定拟音，再通过虚拟歌手调校形成演唱。这里可以借鉴其工作分工；未取得工程文件，不能替作者断言采用了哪个编辑器、怎样逐项映射。

### 2.2 面向方言的 IPA 神经合成已有研究和代码

DiaMoE-TTS 用 IPA 前端、F5-TTS 基础架构和参数高效适配处理多种汉语方言，并提供代码及模型入口。论文的低资源实验包含约三小时专业录制的京剧念白材料。**这类少量数据适配，建立在已有大规模预训练和方言数据基础上，不是从三小时音频白手起家。**

论文评价表也存在较高识别错误率和部分不理想的听感评分，不能只依据摘要把它宣传成已达到商业成品效果；更不能把现代方言、京剧念白上的结果直接当作古楚语结果。

来源：[官方仓库](https://github.com/GiantAILab/DiaMoE-TTS)、[论文 v1，尤其第 4 节](https://arxiv.org/html/2509.22727v1)。这是后续专门训练的研究候选，当前不优先于小规模直接合成试验。

## 3. 路线比较

### A. Eleven v3：最快验证直接 IPA 输入

当前官方文档明确支持在文本中用斜线包围 IPA，通过 `eleven_v3` 生成语音；也有发音词典接口。文档承认相同 IPA 的输出仍可能不一致，而且不同声音的表现会有区别。旧帮助页面与当前开发文档对模型支持范围有差异，试验应记录实际模型 ID，以当前接口文档和结果为准。

来源：[直接 IPA 输入说明](https://elevenlabs.io/docs/overview/capabilities/text-to-speech/best-practices)、[发音词典接口指南](https://elevenlabs.io/docs/eleven-api/guides/how-to/text-to-speech/pronunciation-dictionaries)。

**项目判断：值得先用极少量请求检验。**它省去本地部署，适合先回答“这一串音标能不能变成可用的人声”。但官方的多语言支持没有证明 `ɦˤ`、`kʰˤ` 或特定辅音连缀在古楚拟音中的正确实现。整段纯 IPA 也比普通文本中修正几个词更偏离典型使用方式。

先测试视频中已有字幕依据的单词，再测试整句。不要只发“请用上古楚语朗读”，也不要给生成器同时塞入长段考据说明，让它把解释一起念出。

### B. IMS-Toucan：更适合自行做可控的 IPA 合成

它采用发音特征表示，前端源码有 `input_phonemes=True` 路径，可以直接将输入音素转为特征向量。源码还分别处理送气、唇化、长音、咽化等特征，技术方向与本任务很贴近。[项目](https://github.com/DigitalPhonetics/IMS-Toucan)、[前端源码](https://github.com/DigitalPhonetics/IMS-Toucan/blob/MassiveScaleToucan/Preprocessing/TextFrontend.py)

本次核对到了一个具体问题：特征处理分支用 `ˁ` 标咽化；普通文本转音素的处理里另有 `ˤ → ˁ` 和 `g → ɡ` 的转换。直接音素路径绕过了通常的文字转音素流程，因此不能假定把截图转录原样粘贴就会经历这些转换。缺失音素在默认处理下可能只打印提示而继续。

实现时需要一个很小的输入适配：保留原始 IPA，另存传给引擎的字符串，检查每个音与附加符号实际进入了什么特征。先确认截图所需音，不需要先扩展完整古楚字典。

**项目判断：作为本地开发候选优于单纯依赖文字提示。**不过，能在向量里表示咽化，不等于预训练声学模型已经学会在任意辅音上自然实现咽化；仍需听测。项目的“覆盖数千语言”介绍也不能替代特定古楚拟音的验证。

### C. Synthesizer V：适合吟唱和可精细编辑的短句

官方材料提供音素编辑、音素时序及音素参考表，脚本接口也能设置音素。可以把目标 IPA 映射到引擎接受的音素，安排音高和时长，再逐处调整。[官方音素与帮助资源](https://www.dreamtonics.com/svstudio-resources/)、[音素设置接口](https://resource.dreamtonics.com/scripting/Note.html)、[官方发音调整说明](https://dreamtonics.zendesk.com/hc/en-us/articles/48341716746905-Troubleshooting-Unsatisfactory-Pronunciation)

其输入音素集合不等于完整 IPA；即便能跨语言歌唱，某个声音库仍可能缺少你们想要的发声方式。此时可选明确记录的近似实现、拼接补录，或采用其他合成器。不能仅增加一个自定义符号，就认为模型学会了新音。

**项目判断：对有固定节拍、长元音、反复呼告的吟唱，编辑流程很合适。**可以先尝试元音延长后在句末收住塞音韵尾。它也能用于风格化念唱，但不能保证随便铺几颗等高音符就得到自然旁白。

### D. 正确底稿 → Seed-VC：让发音和角色音色分开处理

声音转换输入的是一段已经发出来的声音，再以另一段参考音色转换。Seed-VC 提供语音及歌声转换；其 V2 还有口音／情绪转换开关。[官方仓库](https://github.com/Plachtaa/seed-vc)

对于古楚拟音，应先采用以保留原读法为目的的音色转换。V2 的 `convert-style` 打开时会进行口音和情绪转换，项目试验应先关闭此项，对照输出是否保留原辅音和收尾。关闭也不等于绝对不改变发音。

底稿可以由播音同学读，也可以来自核对过的 IPA 合成结果。目标音色可以使用团队成员同意使用的录音或合适的现成声音。

**项目判断：当底稿已读准、但音色或角色区别不够时很实用。**它不能把普通话的“玉 yù”自动修成指定的 `ŋuk`；如果原始发音错误，换音色通常不会解决来源问题。

### E. Kokoro、Azure、eSpeak：各有用途，不能只看“支持音标”

| 方案 | 已核实的能力 | 对本项目的限制与用途 |
| --- | --- | --- |
| Kokoro | `KModel.forward` 接受音素字符串 | 源码会过滤词表中没有的字符；先查所选模型词表是否覆盖目标符号。适合覆盖范围内的轻量试验，不能无检查地喂任意 IPA |
| Azure Speech | SSML phoneme 和发音词典 | 能控制发音，但受具体语言、音素集合和声音支持限制；应按目标音逐项核对。不是“任何 IPA 均可合成”的承诺 |
| eSpeak／eSpeak NG | 音素输入及可修改的语言、音素定义 | 适合做可控的基线与练习提示。传统 eSpeak 输入使用自己的 ASCII 音素助记符，不能把 IPA 字符串直接当成同一种编码 |

来源：[Kokoro 模型源码](https://github.com/hexgrad/kokoro/blob/main/kokoro/model.py)、[Azure 发音控制](https://learn.microsoft.com/en-us/azure/ai-services/speech-service/speech-synthesis-markup-pronunciation)、[eSpeak 音素输入说明](https://espeak.sourceforge.net/phonemes.html)、[eSpeak NG 音素文档](https://github.com/espeak-ng/espeak-ng/blob/master/docs/phonemes.md)。

eSpeak 的基线价值在可观察、可修改，不在于自动得到适合 PV 的自然音色。即便之后通过声音转换增强音色，僵硬的音节衔接和错误发音也可能保留。

### F. Qwen3-TTS 等参考音频模型：有用，但先区分两种“零样本”

Qwen3-TTS 官方提供声音克隆、声音设计和自然语言控制，并列出十种主要语言。它没有因此承诺对古楚语进行准确的任意句子发音。[官方仓库](https://github.com/QwenLM/Qwen3-TTS)

“没有训练过这个说话人，也能模仿其声音”和“没有学习过这个语言的字音规则，也能读新句子”是两个不同任务。参考音频可能带来一些口音特征，但不能据此假定文字到古楚音节的映射已经学会。

这类模型可以作为普通话文案、情绪和角色音色的候选，也可纳入 IPA 试验对照组；本次没有确认它们提供与上述音素接口等价的硬性读音控制。不要把自然语言指令的表达控制当作逐音素控制。

## 4. 大模型适合负责哪些工作

文字大模型可以辅助检索词条、整理视频音标、选择语境义项、把已核实音标转换为不同引擎的输入格式、生成批量试音请求，并制作演员练习卡。

建议维护一个简单的词条记录：

`原字／词｜句中义项｜拟音方案与出处｜原始 IPA｜引擎输入｜发音调整说明｜选用音频`

给文字模型的约束可以写成：

> 只使用所附词表和拟音规则。按句中义项选读音，保留原始拟音与引擎输入两列。缺少依据的字标为“待定”，不要用另一套体系或普通话补齐。输出不确定项，供人工选择。

这是让模型帮助维护资料，而不是让它凭记忆编出完整古楚语。图片 OCR 后尤其要检查 `ʔ/ʕ`、`h/ɦ`、`ˤ/ˁ`、`g/ɡ` 和附加符号的位置。

从学术构拟到可听版本，还要选择部分未定成分、音长、连接、句重音与语调。这些选择应在录音稿里明确；模型生成得自然，不能反过来证明这些选择历史上正确。

## 5. 可以直接用于第一次试验的材料

先用你的视频已有字幕作为输入依据，不立即引入新的楚辞句子。下面的 IPA 沿用上一份报告的字幕转录；它是视频作者方案，尚未经本项目音频核查。

### 5.1 单词和短语

| 字／短语 | 目标 IPA | 重点检查 |
| --- | --- | --- |
| 玉 | `ŋuk` | 开头是否保留 ŋ；结尾是否有 k；是否只读一个音节 |
| 以 | `ləʔ` | ə 是否明显偏移；末尾声门闭塞是否消失 |
| 乘 | `ɦləŋ` | 开头的辅音组合是否被拆成多音节 |
| 兮 | `ɦˤe` | 是否保留有声起音和所选咽化实现 |
| 溘 | `kʰˤʌk` | 送气、咽化和韵尾组合；是较难的压力样例 |
| 上 | `dʌŋʔ` | 是否保留目标起音及复合收尾，而不是回到普通话 shàng |
| 玉虬 | `ŋuk grou` | 词间衔接、g 的清浊、辅音连缀是否失真 |
| 以乘 | `ləʔ ɦləŋ` | 前词收尾是否被后词起音吞掉 |

先不要求初学者一次准确判断所有细微音质。可以先检查音节数、漏读、增添元音和关键闭塞；咽化等暂时无法判断的项目如实留待核查，不以“听起来很古老”替代。

### 5.2 Eleven v3 输入示例

按当前官方格式，可分别提交以下短输入：

```text
/ŋuk/
/ləʔ/
/ɦˤe/
/kʰˤʌk/
```

单词可以输出后，再比较按词分开的整句：

```text
/sih/ /ŋuk/ /grou/ /ləʔ/ /ɦləŋ/ /ʔˤi/ /ɦˤe/
```

与连成一段的版本：

```text
/sih ŋuk grou ləʔ ɦləŋ ʔˤi ɦˤe/
```

对应“驷玉虬以乘鹥兮”。这是**候选输入，不是已经验证能正确发音的配方**。两种分组都测试，是为了观察停顿、音节数和连读差异。普通词的重音建议不能机械套成战国楚辞的固定词重音。

### 5.3 第一次小样怎样安排

建议先只选一个后端、一种现成声音。八条单词／短语各生成三次，再试一条整句。目的是确认重复性，不是做完整学术评测。估计半天至一天能完成一轮整理与听审；这是假定已有可用账户或部署环境的项目安排，不是模型实测速度。

逐条记录：音节是否完整、主要音是否保留、同输入是否反复变读、听感是否自然、需要多少人工修补。选中的干声作为固定资产保存，成片中直接复用，不必每次重新合成同一句。

若普通结构能稳定发出，只有少数难音失败，可以局部补录或明确简化；若频繁漏音、增加音节或回读普通话，就不继续靠“更神秘、更古老”的提示词修补，转向音素编辑或真人底稿。

## 6. 如何核对音频，避免生成一个错误教学范本

三个问题分开看：

1. **文献依据**：这串拟音来自哪套方案？这一步不由 TTS 证明。
2. **声音实现**：输出是否接近已经选定的 IPA？既要听，也可以观察音节边界、闭塞与时长。
3. **表演效果**：角色、情绪、节奏是否适合镜头？这一项可以让更多普通听众参与。

普通话 ASR 转写回原汉字，不适合作为古音正确率。识别器可能根据上下文猜中汉字，也可能把正确的拟古读法当成错误。强制对齐也不能单独证明读准：它是在给定文本或音素假设下寻找位置。

可以用 Praat 等工具辅助观察，但单靠一张频谱图或一条音高曲线也无法鉴定所有咽化、清浊与历史语音差别。不要给未经听测的模型输出冠以“标准发音示范”；先称项目选定版本的练习样音。

## 7. 为什么不建议一开始用参考歌训练模型

你提供的视频约四分半，但其中包含音乐、重复和演唱拖腔；可用的独立音节及上下文比时长数字更少。即便完成人声分离，也不会增加原本没有的音素组合，分离还可能改变细节。

对原唱片段做声音克隆，或让模型重复已见歌词，与读准完全新句子是不同难度。成功唱出原歌不能证明已学会完整古楚音系。

若未来确实要大量生成新台词，可以按确定方案录制并标注合成训练材料，再研究 IPA 前端、音素覆盖、微调及未见句子的泛化。训练时要留出含新组合的测试句；不能只用训练歌词评估。所需数据量取决于底模对目标声音的覆盖，不能简单承诺“十分钟就能学会古楚语”。

把未经核对的合成音频重新作为训练数据，会将已有错误传下去。先积累实际项目已经核对过的台词，比先批量造一个庞大的“古楚语语料库”更有价值。

## 8. 本项目的选择

**近期 PV：采用小样筛选，先做有限句子。**

- 旁白：先比较 Eleven v3 IPA 输出与播音同学试读，选发音稳定、表达成立的一种。
- 吟唱：把音素与音高、时长一起编辑，必要处补录；这是最接近你所给参考作品的制作思路。
- 多角色：若已有可靠底稿，再试音色转换；转换前后逐处对照。
- 长期工具：若之后需要持续新增台词，开发一个薄层的“项目词表＋IPA 输入适配＋批量生成”工具，优先验证 IMS-Toucan；暂不从零训练大模型。

本次没有调用付费生成接口、安装模型或上传用户视频，也没有生成可供听审的音频。当前结论是：**现有技术足以支持一个值得开展的小规模制作试验，但准确古楚音的生成效果仍需拿上述样例实测。**
