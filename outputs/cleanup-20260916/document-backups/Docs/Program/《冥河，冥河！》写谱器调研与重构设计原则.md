# 《冥河，冥河！》写谱器调研与重构设计原则

> **正式开发依据：** 后续按[《写谱器设计说明书》](./《冥河，冥河！》写谱器设计说明书.md)执行。用户已确认 JSON 共同协议、Windows 独立应用、单工具直接绘制和保音高试听；本页保留调研当时的建议与取舍，文中的“待确认”不覆盖新说明书已确定条款。

> 更新日期：2026-09-06。用途：后续交互设计、架构设计、实现和验收的常用参考。
> 状态：调研与方案评估，尚未实现新版。用户已明确的产品要求与本文建议分别列出；JSON 字段和预览接口尚未与游戏程序共同定稿。
> 调研方式：本地静态审计、作者文档与操作手册、公开仓库关键源码、作者界面示意图。未实机运行外部编辑器，不把功能介绍等同于体验或性能验证。

## 1. 已明确的产品方向

- 用户是谱师。简单直观来自一致的操作规则、合理默认值和清楚的功能组织；不能靠缺少常用功能来简化界面。
- 使用 Godot 制作独立可执行的写谱器。谱师不需要安装 Godot、打开项目、操作场景树或 Inspector。
- 采用剪辑软件式工作区：上部预览关卡效果，下部横向多轨时间线；空格播放／暂停，预览默认自动演示谱面。
- 修改谱面后预览随之更新；暂停、跳转、循环也必须能查看对应时刻的效果。
- 当前先完整支持生／死两侧 Tap、Hold。队友负责游戏逻辑、调频 Hold 和素音；这里只留扩展边界，不制作后两者的编辑功能。
- 谱面交换格式与写谱器界面、Godot 场景组织解耦。具体格式需要双方确认。
- 本轮仅写文档；不实现、不迁移现有谱面、不执行导出。

旧的《MVP 写谱器架构》保留实现对照与历史方案。其插件优先、旧调频、疾振等目标不能直接作为新版范围。技能内的旧四轨编钟项目画像也已过时，以用户最新说明和现行工程为准。

## 2. 现有实现值得保留什么，为什么需要重构

当前主要流程是：时间线／属性面板发出操作 → Workspace 修改 Document 工作副本 → 完整快照历史与刷新 → 校验 → Chart/Show 保存或 StageRoot 快照预览。

值得保留或重新接入的基础：共享时间换算和游戏语义、工作副本、稳定事件 ID、波形多级峰值缓存与后台生成、已有资源读写经验、正式游戏预览接入方向。是否复用具体代码取决于新的边界，不要求整套照搬。

主要问题：

| 问题 | 静态证据及影响 |
| --- | --- |
| 打开流程与当前资源不匹配 | `chart_editor_workspace.gd` 在解析路径依赖前检查 `chart/stage_show` 非空；当前五关采用延迟加载路径。Document 的直接打开测试不能证明工作区入口正常。 |
| 新建歌曲流程未闭合 | 加载 WAV 只建立波形，没有指定播放音频；歌曲元数据、BPM、首拍偏移、拍号和尾点缺少完整编辑入口。 |
| 创建规则不一致 | Tap/Hold 阵营由工具类型后缀和点击行共同决定，会发生工具与落点含义冲突。 |
| 多选拖动有断点 | `timeline_view.gd` 普通点击命中音符后先替换为单选，再读取拖动集合。 |
| Hold 输入不直接 | 点击创建固定长度，再拖尾部调整；缺少一次拖拽生成以及键盘步进输入。 |
| 属性编辑贴近程序字段 | ID、tick 等直接暴露；多选仅显示数量。单字段变化会重建属性控件，存在打断输入焦点的风险，尚未交互复现。 |
| 拖动数据流偏重 | 当前已在松手时合成一次撤销，但移动过程中反复恢复整个谱面并刷新。应保留手势合并，改用受影响对象的前后值。没有进行性能测量。 |
| 预览不能任意定位恢复 | 工作区预览起点换算漏减首拍偏移；PreviewBridge 删除起点以前开始的全部音符，包括仍持续的 Hold。当前测试明确断言这一裁剪行为。 |
| 保存与编辑状态混在一起 | 玩法校验错误阻止正式保存；恢复稿已有底层接口，但缺少完整用户入口。未完成稿应可保存，能否正式试玩另行判断。 |
| 独立发布未就绪 | 已有 standalone 场景不等于独立产品。现有 `export_presets.cfg` 的游戏导出排除了 `src/tools/**`、`scenes/tools/**`，没有写谱器发布链路。 |

源码入口：`Game/src/tools/chart_editor/`、`Game/addons/minghe_chart_editor/`、`Game/tests/editor/run_chart_editor_tests.gd`。新版验收要补上完整用户流程，不能只测试内部方法调用。

## 3. 外部工具调研记录

以下“借鉴”是本项目的判断；不表示所有工具采用相同架构，也不表示所有功能本期都应实现。

### ArrowVortex：围绕节拍和乐句进行编辑

[作者维护仓库](https://github.com/uvcat7/ArrowVortex)支持节拍细分、音符变换等编辑操作。[History.cpp](https://github.com/uvcat7/ArrowVortex/blob/beta/src/Editor/History.cpp) 将编辑记录及其执行／撤销回调分离，并可组成操作链。

借鉴：复制、平移、镜像应直接作用于选区；一次乐句修改对应一次撤销。不要照搬其底层内存管理或历史序列化实现。

### GrooveAuthor：导航、显示模式和校准各有明确含义

[ChartNavigation](https://github.com/PerryAsleep/GrooveAuthor/blob/main/StepManiaEditor/docs/ChartNavigation.md) 区分按时间、按谱面行及包含变速效果的滚动方式，并提供细分／小节导航和缩略导航。[SongSync](https://github.com/PerryAsleep/GrooveAuthor/blob/main/StepManiaEditor/docs/SongSync.md) 区分编辑器补偿与歌曲偏移。[Hold 长度命令](https://github.com/PerryAsleep/GrooveAuthor/blob/main/StepManiaEditor/EditorActions/ActionChangeHoldLength.cs)只保存该音符的新旧长度。

借鉴：显示比例不决定音乐时间；设备补偿不写入歌曲首拍；简单修改只记录必要状态。本项目默认等秒距横向时间线，无需马上复制所有滚动模式。

### SMEditor：从歌曲导入到试听的连续流程

[基础指南](https://github.com/tillvit/smeditor/blob/master/guide/basic-guide.md)先创建歌曲并加载音频，再设置 BPM 和偏移。数字轨道键直接输入音符，按住键移动游标生成 Hold；鼠标也可拖画 Hold。节拍器用于听节拍，Assist Tick 用于听音符落点。

[ActionHistory](https://github.com/tillvit/smeditor/blob/master/app/src/util/ActionHistory.ts) 将动作、撤销和可选重做封装为历史记录。[自动对齐指南](https://github.com/tillvit/smeditor/blob/master/guide/auto-sync.md)也明确要求人工核对预测结果。

借鉴：鼠标与键盘是同一编辑能力的两种入口；首拍对齐应是建谱流程的一部分。自动 BPM／音符分析可后续添加，不能代替基础定位和人工编辑。

### Moonscraper：歌曲级设置、谱面编辑与试玩分工清楚

[仓库与操作手册](https://github.com/FireFox2000000/Moonscraper-Chart-Editor)展示歌曲级 BPM／拍号／段落与具体乐器难度音符的区分，支持选区整体移动、持续音编辑、段落定位和试玩。源码 `CommandStack.cs` 与 `BatchedSongEditCommand.cs` 分别处理历史与批量修改。

借鉴：全局节奏设置不应淹没在音符属性中；常用动作可以从时间线完成。我们只有生／死两侧，不需要照搬多乐器工作区。

### ArcCreate：编辑与游戏能力共用，操作独立表达

[EventCommand](https://github.com/Arcthesia/ArcCreate/blob/trunk/Assets/Scripts/Compose/History/Commands/EventCommand.cs)记录新增、移除及修改对象的新旧值，通过 Gameplay Chart 服务应用修改。[项目仓库](https://github.com/Arcthesia/ArcCreate)还提供时间、镜头和演出相关编辑能力。

借鉴：预览与游戏共用谱面解释和表现能力，编辑器自己管理操作历史。宏、复杂演出编译等暂不引入；先做好 Tap/Hold 和预览协议。

### Phiedit 2573：缩短局部试听与修改的往返

[作者仓库及操作说明](https://github.com/Chengxuxiaoyuan-2573/Phiedit-2573)提供 Hold 拖画、多选和两种按住试听行为：松键返回起点，或停在试听结束位置。[history.ts](https://github.com/Chengxuxiaoyuan-2573/Phiedit-2573/blob/master/src/managers/renderer/history.ts)以对象属性修改记录和分组支持撤销。

借鉴：保存试听起点、循环选区、快捷试听，让谱师反复检查一个乐句时无需重新定位。该项目参考 RPE，但这里没有审计 RPE 的内部架构，不能把两者混称。

### Majdata：编辑器与预览器职责可以分开

官网链接的 [MajdataEdit](https://github.com/LingFeng-bbben/MajdataEdit) 是 WPF 编辑部分，[MajdataView](https://github.com/LingFeng-bbben/MajdataView) 是 Unity 预览部分；两者仓库已归档，此处作为历史架构参考。

借鉴职责分离，不照搬跨引擎部署。本项目使用 Godot，优先在同一应用内复用游戏预览场景，减少启动、同步和版本管理负担。

### 可反复检查的共通经验

1. 常用操作围绕音乐位置、选区和乐句组织，程序资源字段放到合适的高级入口。
2. 导航、输入、局部试听、修正之间的往返越短，工具越有生产力。
3. 简单直观依赖规则一致和及时反馈；高级能力放入菜单、快捷键与上下文面板，而非删除。
4. 一个手势对应一次撤销；修改、复制及批量操作走同一编辑路径。
5. 预览接近正式游戏，但编辑定位不能受游戏镜头、运动方向或视觉速度限制。
6. 对齐、缓存、格式转换和错误定位服务于制谱，不应成为谱师必须理解的内部流程。

## 4. 剪辑软件式工作区的具体含义

建议工作区布局如下，尺寸比例可拖动调整；这只是结构草图，尚未定视觉样式。

```text
┌──────────────── 菜单与常用操作 ─────────────────┐
│ 歌曲／素材／段落 │       实时关卡预览       │ 属性 │
│                │  保持游戏画面比例        │ 面板 │
├──────────────── 播放／时间／吸附 ────────────────┤
│ 秒时间尺        00:10       00:11       00:12    │
│ 小节与节拍      波形、首拍、BPM、段落标记        │
│ 生钟音符轨      Tap     ━━━ Hold ━━━           │
│ 死钟音符轨          Tap       Tap              │
├──────────────── 状态与可展开的问题列表 ─────────┤
└───────────────────────────────────────────────┘
```

默认两条音符轨分别对应生、死。Tap/Hold 放在同一侧的轨道上，用形状区分，便于看双手分配和同侧冲突；不是每种音符机械地增加一行。轨道是谱面事件的组织方式，不等于要增加一份音频流。

空格在工作区播放／暂停；编辑文字时仍输入空格。单击时间尺定位，拖动游标刷新预览；拖动音符会显示候选位置／长度，松手提交，Esc 取消。音符选择不应随便覆盖循环区间，时间区间选择与对象选择要有明确操作区别。

剪辑软件的选择、吸附、缩放、波形、段落、循环和属性面板都适合借鉴。波纹删除、自动推移后续素材等操作不能默认照搬，否则删除一个音符可能意外改变后续音乐位置。

### 常规制谱能力不能省略

| 工作阶段 | 新版基础能力 |
| --- | --- |
| 建谱 | 新建／打开／最近项目；音频导入与替换、元数据、首拍偏移、BPM／拍号编辑、谱面结束位置 |
| 定位 | 秒时间尺和小节／拍辅助尺、节拍细分吸附、临时关闭吸附、波形、缩放／平移、段落跳转 |
| 输入与修改 | Tap 点击／键盘输入、Hold 拖画／键盘延长、头尾调整、框选／增减选、整体移动、跨侧移动、生死互换、复制粘贴／重复／删除、量化、批量属性、撤销重做 |
| 检查 | 空格播放暂停、任意定位、选区循环、变速试听、节拍器／音符提示音、实时自动预览、必要时切入手动试玩 |
| 管理 | 保存／另存为、恢复稿入口、资源缺失提示和重新定位、问题定位、可移交谱面包 |

功能可以分迭代实现，但不能把这些长期从目标中删掉。自动制谱、复杂宏、联网协作、任意 VFX 时间轴等不属于当前 Tap/Hold 基础闭环。变速要明确是否保音高；现有 `pitch_scale` 会同时变调，不应标为保音高功能。

## 5. 实时预览：最主要的工程工作

Godot 的 [SubViewport / SubViewportContainer](https://docs.godotengine.org/en/stable/tutorials/rendering/viewports.html)可将关卡渲染嵌入应用界面。这里建议直接显示其渲染纹理，不走每帧截图再上传图片的路径。

但嵌入画面只是容器问题。当前 StageRoot 及快照桥不能直接保证编辑预览要求，需要与游戏程序约定以下行为：

| 场景 | 必须达到的效果 |
| --- | --- |
| 暂停后修改音符 | 当前位置保持不变，预览更新，允许查看未保存内容 |
| 正常播放 | 自动完成 Tap/Hold，能看到实际反馈、钟的持续状态及其视觉结果 |
| 拖到 Hold 中段 | Hold 和持续效果仍存在，不能删除整个 Hold 来绕过状态恢复 |
| 往回跳／循环回起点 | 清除上一轮残留的判定、声波和临时表现，再重建目标时刻的状态 |
| 播放中修改 | 保持播放位置，不叠加另一份歌曲音频；以当前编辑版本更新相关内容和预览状态 |
| 调整 BPM／偏移 | 明确保持当前音频秒位置；重新计算该时刻的拍位置及预览，不意外跳动音乐 |

建议由一个播放控制器拥有当前位置、暂停、速率和循环；音频、时间线游标、自动输入与预览读取同一时间基准。当前游戏 SongClock 使用与音频起播对齐的单调时钟，不能误写成直接以播放器观测位置驱动判定，也不应另建逐帧 delta 累加的编辑器判定时钟。

自动预览优先复用正式判定与表现链，通过理想时刻的自动输入完成音符。只把音符涂亮或把 MISS 关闭，不能正确展示 Hold 载波等实际效果。正式玩家成绩／存档不由编辑预览写入。

任意定位时，纯时间函数能直接求值的动画直接求值；依赖历史输入的状态通过重置与确定性快进恢复。首先保证 Tap/Hold 正确，再依据实测定位开销决定是否需要稀疏状态缓存。不能为所有时刻预建巨大快照，也不能假定 GPU 粒子、传播声波会随时钟跳转自动恢复。相关随机表现、种子与回放能力需双方约定。

接口只需覆盖：装入／更新谱面、定位并重建状态、播放／暂停／速率、自动演示／手动试玩。具体方法名及状态结构未定，不提前建立通用插件协议。

## 6. 秒时间轴与音乐时间可以同时成立

建议默认横轴按音频秒数等距排列，与用户的剪辑软件思路一致；主游标显示 `分:秒.毫秒`，节拍尺、吸附和属性辅助显示小节／拍。

音符持久化仍建议使用整数 tick，默认沿用当前 PPQ=480（每四分音符 480 tick）。BPM 决定拍在时间轴上的实际宽度；拍号决定小节划分，不改变 tick 的速度。这样按秒试听、按波形定位与按拍创作不会互相排斥。

建议交换格式的含义：

`音频位置 = 首拍偏移 + 从 tick 0 积分到音符 tick 的节奏时间`

例如首拍位于音频 2 秒，120 BPM，PPQ=480，则 tick 960 位于音频 3 秒。若 Hold 长 960 tick 且跨越 BPM 变化，尾点应由“起始 tick + 长度”再换算，不能用头部 BPM 乘整段长度。

暂停与定位以音频位置为准。鼠标自由放置转换成最近的可表示 tick；关闭吸附表示关闭节拍网格约束，不宣称无限精度。需要亚 tick 精度时再共同调整 PPQ 或协议，不存两套互相矛盾的音符秒数与 tick。

本机输出／试听补偿保存在工具设置，不写入共享首拍偏移。当前还存在 `chart_offset_ticks`；若新协议只保留首拍偏移，迁移必须处理该字段对 BPM 变化与事件时间的影响，不可静默丢弃。

## 7. 谱面格式解耦建议（待双方确认）

### 7.1 分清三个用途

| 内容 | 建议表示 | 使用方 |
| --- | --- | --- |
| 正式歌曲与谱面语义 | 有版本的 JSON、相对音频路径、稳定素材键 | 写谱器和游戏共同理解 |
| 工作区状态 | 单独的可选编辑器设置文件：缩放、滚动、折叠、循环区间等 | 写谱器；不改变判定 |
| 游戏运行对象 | 现有 SongChart / NoteEvent / CompiledChart 等 Resource 或内存对象 | 游戏及复用它的预览 |

推荐 JSON 作为外部交换格式，`.tres` 可继续作为游戏内部格式和旧谱兼容入口。理由是当前 `.tres` 引用具体脚本与 `res://` 资源组织，容易让谱师文件依赖工程内部目录。并非 `.tres` 不能独立加载，而是纯数据协议更适合双方并行开发和交付。

更换扩展名本身不产生解耦。关键是 UI 只发出语义编辑操作；读写器负责协议转换；游戏读同一套经过定义的语义，不从控件状态、节点名称或 Godot 数字枚举推断音符。

```text
图形编辑操作 → 谱面文档 → 公共读写器 → JSON 谱面
                  ↓                     ↓
             游戏适配与编译 ← 公共读取与语义校验
                  ↓
            游戏内部对象 → 实时预览／正式游玩
```

可在内存中继续使用类型化 Resource，不必为了采用 JSON 重写整个领域层。应避免写谱器一份时间转换、游戏另一份时间转换。读写适配可以是少量明确函数，不需要动态插件框架。

### 7.2 包装形式建议

工作时使用普通目录，内容如 `song.json`、`charts/normal.json`、`audio/song.ogg` 和可选编辑器状态。交付时可将同样的目录内容打成 ZIP；只是搬运包装，不引入第二套谱面语义。`.minghe` 等专用扩展名尚不确定，暂用可读的标准扩展名讨论。

歌曲级数据负责身份、标题、作者和音频引用；谱面级数据负责难度、谱师、时间映射和音符。新协议建议将首拍偏移与 BPM 表放在同一份谱面 timing 中，以支持同歌不同谱的时间设置；这与当前 SongDefinition 保存首拍偏移不同，需要游戏适配，不能冒充既有事实。音频裁剪或替换后必须提示重新检查对齐。

内置美术通过素材键／主题键引用；外部音乐与允许导入的素材使用包内相对路径，不记录谱师电脑绝对路径。关卡标题、奖励、解锁规则等应由歌曲／关卡层承载，不混入每个音符的导出对象。

Godot 支持[运行时加载外部音频与文件](https://docs.godotengine.org/en/stable/tutorials/io/runtime_file_loading_and_saving.html)。独立写谱器应采用运行时导入路径，不能要求谱师通过 Godot 的资源导入面板准备音乐；波形缓存也不应成为谱面交付的必需文件。

### 7.3 第一版需要确认的字段

| 层级 | 建议字段与含义 |
| --- | --- |
| 格式 | `schema_version`：交换协议版本，与现有 `.tres` schema 版本明确区分 |
| 谱面身份 | `chart_id`、`song_id`、难度标识、谱师信息 |
| 时间 | `ppq`、`first_beat_offset_ms`（正值表示首拍更晚）、`tempo_events`、`meter_events`、`end_tick` |
| 音符身份 | 稳定 `id`；现有 `group_id`、`damage_group_id` 的语义需保留或明确定义迁移 |
| 音符基础 | `kind` 字符串、稳定侧别标识（建议沿用 `zhu/xuan`）、`tick`、`duration_ticks` |
| 音符外观 | 可选 `visual_variant`，只影响表现 |
| 段落 | 标记位置及名称；不保存运行时判定结果 |

Tap 长度为 0，Hold 长度为正。序列化顺序稳定，撤销、移动不会改换事件 ID。删除后再撤销恢复原 ID；复制创建新 ID，并处理组合引用。

### 7.4 给调频 Hold 留余地

已知方向是 Hold 变体，但还不知道方向切换、连续参数、判定节点的最终语义。现在只保证音符基础字段不会强迫所有音符只能是“一个点”，未来能够附加有类型的行为数据。

可讨论的方案是 Hold 携带命名的行为扩展；到底采用 `hold` 加行为，还是独立类型，等队友定玩法后确认。现在不导出空曲线、不猜测四方向字段、不定义摇杆采样协议。行为内的点若采用时间，届时必须明确相对 Hold 起点还是绝对谱面 tick。

扩展不能变成无约束的任意字典：每种已支持行为仍要有具体语义和版本规则。也不能把判定行为塞进 `visual_variant`。

对于结构兼容但不支持的类型／字段，编辑器只修改自己理解的部分并保留其他数据；无法可靠保留或无法理解的重大版本，明确提示并保持原文件，不静默删除，不把未知音符降级成 Tap。旧调频滑条也不能自动宣称等价于新调频 Hold。

## 8. 独立交付与协作边界

推荐同一个 `/Game` 代码库中共享领域和表现模块，以独立入口、发布配置产出写谱器。谱师获得独立应用与它需要的资源；独立可执行不要求复制出一套游戏源码。Godot 的[导出机制](https://docs.godotengine.org/en/stable/tutorials/export/exporting_projects.html)可作为发布基础，具体入口选择和资源筛选留给实现阶段验证。

由写谱器侧负责工作区、编辑操作、历史、歌曲导入、波形、文件管理与协议读写接入；由游戏侧负责音符语义、正式判定、运行时编译与表现。共同确认时间定义、谱面协议、预览控制接口和兼容样例。预览用哪版游戏规则／美术应能辨认，旧版工具不会自动获得队友尚未集成的新效果。

下一轮应先共同确认：

1. JSON 交换格式及歌曲／谱面／关卡数据边界；时间与分组字段迁移办法。
2. 预览状态重建、自动输入、音频唯一控制权的归属。
3. 一段典型乐句的逐步交互稿及第一版完整功能清单。

## 9. 后续设计与验收时的使用方法

开始新版写谱器相关工作时先阅读第 1、4、5、7 节；变更决定时记录日期、原因以及替代了哪条方案。外部项目经验是参考，不高于用户后续决定。

验收以真实流程为准：

- 在没有 Godot 编辑器的电脑上，新建歌曲、导入音乐、对齐首拍、制作并保存一段 Tap/Hold。
- 框选一组音符，拖动其中一个时保持整组；撤销一次回到原状态。
- 一次拖拽画出跨小节 Hold，并可改头尾、复制与交换侧别。
- 首拍偏移非零、BPM 发生变化时，波形、网格、提示音、预览与导出后游戏一致。
- 定位到 Hold 中段，正向播放、回拖、循环和暂停修改后，持续状态正确且没有重复音乐或残留特效。
- 保存未完成稿，关闭重开继续工作；导出包换目录／换电脑仍能找到音乐。
- 无编辑改动的导入导出不丢失分组、外观与可保留扩展；重大不兼容不会被静默改写。

本轮没有代码修改、运行测试或导出产物。以上验收项目是后续目标，不是已通过的测试结果。
