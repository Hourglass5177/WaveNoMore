# 自动节奏识别开发与验证记录

日期：2026-09-07。实现范围为编辑器侧离线识别、候选修正、固定 BPM 应用和 Tap 草稿。正式玩法规则、JSON 协议不变。

## 实现与来源

- [Beat This! 官方实现](https://github.com/CPJKU/beat_this)：采用 1.1.0 的 `Audio2Beats`，官方 `final0` 本地权重，CPU／FP32／`dbn=False`，保留官方预处理、分块边界与后处理。公开代码、权重采用 MIT 许可。
- [librosa beat_track](https://librosa.org/doc/main/api/generated/librosa.beat.beat_track.html)：作为拍点与 BPM 算法参考，没有作为小节重拍检测器接入。
- [PyInstaller onedir](https://pyinstaller.org/en/stable/usage.html)：独立目录携带推理运行时，无用户 Python 依赖。确切版本见 `tools/rhythm_analyzer/requirements-lock.txt`；当前 torch 2.14.0+cpu、torchaudio 2.11.0+cpu，`pip check` 通过，实际推理通过。

`StudioRhythmJob` 独占后台解码线程与子进程；音频通过 Godot 的独立 playback 解码成 PCM16 单声道 WAV。任务 JSON 使用请求编号，阶段结果原子替换。取消结束当前子进程，换歌和换工程使旧结果失效。音频路径、修改时间、大小、范围、分析器版本决定缓存复用。读取缓存不会修改谱面。

分析器用中位间隔建立整数拍编号，允许漏拍；去掉偏离拟合的点后重新做线性拟合。小节拍号只建议 3/4 或 4/4；至少两个重拍间隔、70% 一致才给出建议。该比例是启发式条件，不是准确率。局部网格偏差、检测空白及小节相位冲突以候选问题显示。

`StudioRhythmPanel` 保持候选、原始结果和草稿；`StudioRhythmTools` 负责时间映射应用和生成查询。正式冲突区间提取自 `ChartValidator`，与游戏校验共用边界规则。点击“应用”或“确认生成”才进入文档历史。按当前 `chart_offset_ticks` 反算首拍偏移，既有 Hold 不拆分。取消候选不产生历史。

## 本机测量

Windows，Intel Core Ultra 9 185H，RTX 4060 Laptop（推理不使用 GPU），Godot 4.7.2 Compatibility。以下是单次本机观察值，不是其他电脑的性能保证。

| 样本与项目 | 结果 |
|---|---|
| 用户原曲《冥河demo-v1.wav》 | 92.174 秒、48 kHz、立体声 PCM24；仅只读访问 |
| 独立环境 Python 首次进程推理 | 10.54 秒 |
| 打包 EXE 新进程推理 | 8.94 秒；峰值工作集 477,585,408 字节，约 455 MiB |
| 五分钟音频后台端到端 | 21.76 秒，含一次启动／取消及第二次解码、识别；识别器内部 18.22 秒 |
| 五分钟测试取消 | 7.07 ms |
| 分析期间渲染帧间隔 | 中位 5.32 ms，95 分位 9.86 ms |
| 分析期间预览额外重建 | 0；音乐持续播放 |
| 同一输入再次分析 | 命中缓存，没有启动子进程 |
| 小样本候选 BPM 修改 | 100 次同步更新平均约 0.017 ms；不含显示器呈现延迟 |
| 五分钟网格诊断 | 600 拍，100 次候选变化平均约 0.20 ms |
| 向一万音符谱面查询每拍草稿 | 从全表比较的 5048.60 ms 降至时间区间扫描的 95.41 ms；同样生成 501 个、跳过重复 100 个 |

五分钟样本是将用户原曲循环到 300 秒的性能夹具，接缝并非正常编曲，不能当作准确率语料。原曲模型拟合约 138.276 BPM，中位偏差 26.46 ms、95 分位 56.13 ms；拍号未确定。用户也不知道人工标准 BPM／拍号／首拍，因此这些数字**未通过准确率验收**。

独立 EXE 已在临时工作目录、仅 System32 的 PATH、未传入 PYTHONHOME/PYTHONPATH 的子进程中跑通，读取开发包内模型。缺失模型时明确失败，不下载替代模型。没有真正执行断网干净 Windows 虚拟机测试，不能将上述隔离进程测试等同于该验收。

## 回归与可复现入口

- `tests/editor/run.ps1`：九组写谱器测试通过。新增测试覆盖非零全谱偏移、Hold 保留、一次撤销、变拍号、排除范围、冲突与重复跳过、候选不编译、重开候选、空格播放及三种格式的一秒解码。
- `tools/rhythm_analyzer/test_analysis.py`：合成 3/4、4/4、漏拍／抖动、拍号不确定、拍点不足，共三项测试通过。这只验证拟合，不验证模型识别。
- `tests/editor/measure_rhythm_integration.gd`：需要本地 `builds/rhythm-probe/five_minutes.wav`，运行独立识别器并记录播放、帧间隔、取消及缓存。音频不随 Git 或开发包分发。
- 领域测试仍为已有的 7 项失败：核心 1/131（暂停重新按住 Hold）、调频 6/101（提前完成及回退状态）。与 `chart-editor-progress.md` 的既有记录一致，未修改玩法以使它们通过。
- 渲染界面检查截图：`builds/stability/rhythm-workspace.png`；日志与测量原始 JSON 在 `builds/stability/`、`builds/rhythm-probe/`。

## 待完成的发布验收

需要有人工标注的真实 3/4、4/4、弱起、长前奏、稀疏打击、半速歧义曲目，分别记录 BPM、拍点和小节首拍错误；目前只有一首未标注实曲，不能宣称识别质量已全面通过。三种格式当前验证了独立解码及相同秒数的输出长度，尚未通过同源音频转码的逐拍时间基准误差验收。

还需干净、离线且未安装 Python 的 Windows 机器验证整包启动，以及长时间人工制谱检查。开发包可用于试用和采集这些结果，用户原始歌曲与“测试”工程不打包、不覆盖。

开发包约 264 MiB（压缩 ZIP），主要增加来自 CPU 推理运行时和约 77 MiB 的模型。包内按显式清单包含主 EXE、识别器、模型、许可、使用说明和合成示例工程。PyInstaller 收集时提示训练数据集模块缺少 pandas；运行时不导入训练模块，独立推理已实测成功，没有为训练功能安装额外依赖。
